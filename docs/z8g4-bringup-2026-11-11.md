# z8g4 bring-up notes (2026-11-11)

Factual log of bringing the llama.cpp SYCL Qwen3.8-27B Q4_K_M stack up on
host **z8g4**. No secrets or tokens are recorded here.

## Host

- HP dual-socket machine, 88 CPU cores, 231 GB RAM, Ubuntu, Docker.
- Two Intel Arc Pro B70 (BMG_G31_B70, device id `0xE223`):
  - PCI `0000:17:00.0` — NUMA node **0**
  - PCI `0000:9b:00.0` — NUMA node **1**
- The two cards sit on **different CPU sockets**. This was confirmed with:
  ```bash
  cat /sys/bus/pci/devices/0000:17:00.0/numa_node /sys/bus/pci/devices/0000:9b:00.0/numa_node
  # 0
  # 1
  ```
- Other GPUs and render nodes are also present (including an RTX 5060 Ti).
  Do not bind all of `/dev/dri` into the container.
- Existing llama.cpp slots: 8010 (b70a coder), 8012 (b70b reviewer), 8014 (test).
  This stack uses host port **8016**.
- Models live under `/opt/models/Qwen3.8-27B-GGUF/`.

## Fixes applied during bring-up

These are in this branch; defaults stay at the lab/upstream values unless
noted.

1. **Build job count.** `cmake --build ... -j$(nproc)` is `-j88` on this host
   and froze the machine during the SYCL compile. `-j24` finished in
   **287.9 s** and used about **40 GB** of RAM. The Dockerfile now takes
   `ARG BUILD_JOBS=24`, passed through compose as `${BUILD_JOBS:-24}`.
2. **`/dev/dri/by-path` mount.** Per-device binds of
   `/dev/dri/by-path/pci-0000:17:00.0-render` (and the sibling card) made
   Compose report `invalid volume specification` because of the colons in
   the name. Compose now bind-mounts the whole folder read-only:
   `/dev/dri/by-path:/dev/dri/by-path:ro`.
3. **oneAPI `setvars.sh`.** The entrypoint runs under `set -u`. Sourcing
   `/opt/intel/oneapi/setvars.sh --force` then aborted with exit 1 (unset
   variables inside the script). The source line is wrapped with
   `set +u` / `set -u`.
4. **Render node renumbering after reboot.** PCI addresses are stable;
   `/dev/dri/renderD*` numbers are not. After this reboot the mapping was:
   - `0000:17:00.0` → `renderD129` (B70)
   - `0000:2f:00.0` → `renderD128`
   - `0000:8f:00.0` → `renderD130`
   - `0000:9b:00.0` → `renderD131` (B70)

   `.env` still had `DRI_RENDER_1=renderD130` for the second B70, which
   produced `invalid device: SYCL1`. It had to be changed to `renderD131`.
   Recheck after every reboot with `./scripts/find-intel-render-nodes.sh` or
   `./scripts/resolve-dri-from-bypath.sh --write .env`. Resolution cannot be
   done inside the container: Docker passes render nodes in `devices:` at
   container create time, before the entrypoint runs.
5. **Cross-GPU comm knobs** (`GGML_SYCL_COMM_SINGLE_KERNEL`,
   `GGML_SYCL_COMM_DIRECT_Q8`, `GGML_SYCL_DEV2DEV_MEMCPY`) are overridable
   from the environment instead of being hard-coded in `entrypoint.sh`.
   Defaults remain `1`, `2`, and `0`.
6. **`HF_TOKEN`** is passed through compose as `${HF_TOKEN:-}`. Source it
   from a secrets manager; never commit a token (`.env` is gitignored).
7. **Optional API key.** `LLAMA_API_KEY` is passed through as
   `llama-server --api-key` when set. Without a key, llama-server warns
   about CORS `*`.
8. **`scripts/bench-api.sh`.** The ~32k-prompt test failed with
   `/usr/bin/python3: Argument list too long` because the prompt was passed
   as a single argv element (Linux `MAX_ARG_STRLEN` is 128 KiB). The prompt
   is now written to a temp file and read from disk.

## Single-GPU results (verified)

`GPU_COUNT=1`, `CTX_SIZE_OVERRIDE=32768` came up healthy
(`GET /health` → `{"status":"ok"}`).

512-token generation, short prompt (27 tokens), two runs of the same
request (`max_tokens=512`):

| Run | Prompt tok/s | Decode tok/s | Prompt ms | Predicted ms | Predicted tokens |
|-----|-------------:|-------------:|----------:|-------------:|-----------------:|
| 1 (cold) | 29.09 | **25.21** | 928.01 | 20309.02 | 512 |
| 2 (warm) | 100.66 | **24.12** | 268.23 | 21229.54 | 512 |

This is well above a 9 tok/s floor, and faster than the earlier Flash-Next
figure of 11 tok/s at 8K on this host. The model, the JIT build, and a
single B70 are fine.

The first `./scripts/bench-api.sh` short-prompt run only generated 2 tokens
(too few for a stable speed number), and the 32k test hit the argv-length
bug above. Use the 512-token curl/timings figures as the single-card
baseline.

## TP2 on this dual-socket host

Tensor split (`GPU_COUNT=2`, `--split-mode tensor`) does not work with the
lab/upstream comm defaults on z8g4. It does start and serve traffic when
copies are forwarded through host memory, but it is slower than a single
card. The published ~51 tok/s TP2 decode figure has **not** been reproduced
here. Recommendation for this host: **`GPU_COUNT=1`**.

### Defaults (`COMM_SINGLE_KERNEL=1`, `COMM_DIRECT_Q8=2`)

The server loads the model (~23 GB per card) and then hangs forever at the
first GPU dispatch. GPU utilization stays at 0%. `/health` remains 503
`Loading model`. Logs stop at:

```
SYCL doors | mmvq_phase : dev=0 arch=intel_gpu_bmg_g31 -> stock chunk order [auto: PVC only]
```

(with a matching `dev=1` line sometimes visible depending on how far the
startup banner got). The container does not crash; it just never becomes
ready.

### `GGML_SYCL_COMM_DIRECT_Q8=0` alone

Same hang, same last log line. Direct-copy-off was not sufficient.

### `GGML_SYCL_COMM_SINGLE_KERNEL=0`

No hang. The process aborts during the first all-reduce with:

```
level_zero backend failed with error: 39 (UR_RESULT_ERROR_OUT_OF_DEVICE_MEMORY)
Exception caught at file:/build/llama.cpp/ggml/src/ggml-sycl/ggml-sycl.cpp, line:1599, func:operator()
SYCL error: CHECK_TRY_ERROR(q_dst.memcpy(ptr_dst, ptr_src, size).wait()): Exception caught in this line of code.
  in function dev2dev_memcpy at /build/llama.cpp/ggml/src/ggml-sycl/ggml-sycl.cpp:1599
```

The backtrace goes through `ggml_backend_sycl_comm_allreduce_tensor` →
`llama_decode` during `load_model`. The cards are not actually full (the
same weights load successfully in single-GPU mode, and the TP2 hang also
showed the model already resident at ~23 GB/card). This looks like a failed
peer copy being reported as an OOM.

### Hypothesis

**Hypothesis (confirmed by the host-forward run below):** cross-socket
peer access between these two B70s is not supported or not working.
`COMM_SINGLE_KERNEL=1` has one card read and write the other card's memory
directly; that path hangs across the two sockets. With that off,
`dev2dev_memcpy` still tries a card-to-card copy and the Level Zero driver
fails. Forwarding those copies through host RAM avoids the peer path and
lets TP2 start.

### Host-forward copies (verified, 11:57 AM CST, 2026-11-11)

Settings: `GPU_COUNT=2`, `CTX_SIZE_OVERRIDE=32768`,
`GGML_SYCL_COMM_SINGLE_KERNEL=0`, `GGML_SYCL_COMM_DIRECT_Q8=0`,
`GGML_SYCL_DEV2DEV_MEMCPY=2`. The server started and `/health` returned
ok.

Same 512-token generation test as the single-card baseline (27-token
prompt, `max_tokens=512`, two runs):

| Run | Prompt tok/s | Decode tok/s | Prompt ms | Predicted ms | Predicted tokens |
|-----|-------------:|-------------:|----------:|-------------:|-----------------:|
| 1 | 92.32 | **16.22** | 292.48 | 31558.69 | 512 |
| 2 | 102.94 | **16.95** | 262.29 | 30211.91 | 512 |

Single-GPU decode on the same host, same test, was **25.21** and
**24.12** tok/s. Host-forward TP2 is about **33% slower** than one card
((16.22 + 16.95) / (25.21 + 24.12) ≈ 0.67).

### Conclusion and recommendation

On this dual-socket host (B70s on NUMA nodes 0 and 1), TP2 works only with
host-forwarded copies, and that path is slower than running on a single
card. **Use `GPU_COUNT=1` here.** The published ~51 tok/s TP2 figure
likely needs both cards on the same socket or root complex.

A commented dual-socket profile with the verified host-forward settings is
in `examples/z8g4.env`. It is marked as verified working, but slower than
single GPU, and is not the recommended default on z8g4.
